# 청구 시스템 구조

> 테스트용 자료(FIXTURE) — 실제 프로젝트 구조가 아니다.

## 모듈 구성

청구 시스템은 청구서 모듈, 구독 모듈, 정산 배치로 나뉜다. 결제 승인은 외부 결제 대행사가 맡는다.

## 정산 배치 구성

정산 배치는 매일 새벽 2시에 전날 결제와 환불을 모아 대행사 정산 파일과 맞춘다. 이 절은 표와 코드 블록이 섞인 긴 절이며 조각 분할 경계를 시험한다.

배치는 수집, 대조, 보고의 세 단계로 이뤄진다. 수집 단계는 결제 기록과 환불 기록을 하루 단위로 모으고, 대조 단계는 대행사 정산 파일의 줄마다 내부 기록을 찾는다. 보고 단계는 맞지 않는 줄을 모아 운영 채널로 보낸다.

대조 결과는 다음 값 중 하나다:

| 결과 | 뜻 | 후속 처리 |
|---|---|---|
| 일치 | 금액과 건수가 같다 | 없음 |
| 누락 | 대행사 파일에만 있다 | 수집 단계를 다시 실행한다 |
| 초과 | 내부 기록에만 있다 | 대행사에 문의한다 |
| 금액 차이 | 건은 같고 금액이 다르다 | 운영자가 직접 확인한다 |

배치 실패 알림은 단계마다 다르다. 수집이 실패하면 30분 뒤 한 번 다시 실행하고, 그래도 실패하면 운영 채널에 실패 알림을 보낸다. 대조 단계의 실패는 다시 실행하지 않고 바로 알린다.

재처리 절차는 운영자가 날짜를 지정해 배치를 다시 돌리는 것이다. 재처리는 같은 날짜의 이전 결과를 덮어쓰며, 덮어쓰기 전 결과는 보관 테이블로 옮긴다:

```sql
INSERT INTO settlement_archive SELECT * FROM settlement_result WHERE batch_date = :date;

DELETE FROM settlement_result WHERE batch_date = :date;
```

재처리 뒤에는 보고 단계만 다시 보내고, 이미 해결된 차이는 보고에서 뺀다. 같은 날짜를 하루에 세 번 넘게 재처리하면 운영 책임자의 확인이 필요하다.

대행사 정산 파일은 대행사마다 형식이 다르다. 배치는 파일을 읽기 전에 대행사별 변환기로 공통 형식으로 바꾸고, 변환에 실패한 줄은 대조하지 않고 따로 모아 보고 단계에 넘긴다. 변환기의 버전은 정산 결과에 함께 기록한다.

환불이 결제와 다른 날짜에 정산되는 경우가 있다. 이런 환불은 원래 결제 날짜가 아니라 환불이 정산된 날짜의 배치에서 대조한다. 대조 결과가 누락이면 전날과 다음 날의 결과를 함께 확인한다.

정산 금액의 합계는 통화별로 따로 계산한다. 환율 변환은 정산 배치에서 하지 않고, 회계 보고가 맡는다. 같은 결제가 두 통화로 기록되어 있으면 금액 차이로 보고한다.

배치는 같은 날짜에 두 개가 동시에 돌지 않도록 날짜별 잠금을 쓴다. 잠금을 얻지 못한 배치는 실패로 끝나지 않고 다음 주기에 다시 시도하며, 잠금이 한 시간 넘게 풀리지 않으면 운영 채널에 알린다.

정산 결과는 운영 화면에서 날짜별로 볼 수 있다. 화면은 일치, 누락, 초과, 금액 차이의 건수와 금액 합계를 보여 주고, 차이가 있는 줄을 내려받을 수 있게 한다. 내려받은 파일에는 카드 번호나 결제 수단 토큰을 넣지 않는다.

정산 배치의 실행 기록에는 시작 시각, 끝난 시각, 단계별 처리 건수, 재처리 여부를 남긴다. 실행 기록은 1년 동안 보관하고, 재처리 기록은 원래 실행 기록과 같은 날짜로 묶어 볼 수 있게 한다.

정산 파일의 보관 기간은 5년이다. 보관 기간이 지난 파일은 분기마다 지운다.

## 청구서 모듈

청구서 모듈은 청구서 발행과 재발행, 취소를 맡는다. 발행 시점과 재발행 규칙은 청구 업무 규칙을 따른다.
